## Introduction

{/* AUTHOR: two or three sentences on what confused you most when you started, and what this page will make clear. */}

The [Quickstart](../quickstart/) gave you a node and an app. This page explains what they do, using commands you can run against your own node. Since 2026-05-07, adding an app key needs no blockchain transaction. A read node passes the messages you send it on to the validators.

## Prerequisites

- A synced node from the Quickstart, or any Snapchain node whose HTTP API you can reach.
- `curl` and `jq`.
- To post: a Farcaster account. Reading needs no account.

Set `NODE` to your app's address. Caddy passes `/v1` to the node:

```bash
export NODE=https://<name>
```

Port 3381 is closed to the internet by default. To reach it straight from your computer instead, open an SSH tunnel in another terminal, then use `NODE=http://127.0.0.1:3381`:

```bash
ssh -N -L 3381:127.0.0.1:3381 root@$IP
```

## Step 1: App keys are gasless now

An app posts for you with an **app key**. The docs also call it a *signer*. It is an ed25519 key pair. Since engine version V16 went live on mainnet on 2026-05-07, you add one by sending a `KEY_ADD` **message** to a node. Before that you had to send a transaction on OP Mainnet and pay for it in ETH. Sources: [writing-messages guide](https://snapchain.farcaster.xyz/guides/writing-messages), and the V16 date and `GaslessSigners` feature in [`src/version/version.rs`](https://github.com/farcasterxyz/snapchain/blob/fc87f2686472598143062a00e1c2b2633b2d87ab/src/version/version.rs).

A `KEY_ADD` holds three signatures:

| Signed by | What | Why |
|---|---|---|
| Custody address (EIP-712, domain `Farcaster KeyAdd`, chainId 1) | `KeyAdd(fid, key, keyType, scopes, ttl, nonce, deadline)` | You approve this key, with these permissions, for this long |
| Custody address of `requestFid`, the app's FID (same domain) | `SignedKeyRequest(requestFid, key, deadline)` | Says which app asked for the key. Our app uses your own FID, so your custody key signs both. |
| The new app key | The message envelope | Shows the app has the private half |

What the node checks (`key.rs` at v0.14.3, see SOURCES.md):
- `nonce` is above `currentUserNonce` from `GET /v1/signersByFid`. The app sends `currentUserNonce + 1`.
- `ttl` is between 1 second and 90 days. Each use of the key moves the expiry forward by the ttl again.
- At most 16 scopes. `KEY_ADD` and `KEY_REMOVE` can never be scopes. At most 1000 gasless keys per FID.
- `deadline` counts seconds since 2021-01-01 UTC (Farcaster time).

```bash title="Your nonce and keys"
curl -s "$NODE/v1/signersByFid?fid=<your-fid>" \
  | jq '{currentUserNonce, gaslessSignerCount, gaslessSignerLimit, signers: [.signers[] | {source, scopes, ttl}]}'
```

Scopes and a lifetime only exist on gasless keys. For keys added onchain the node sends no `ttl`, so jq prints `null`; `scopes` may be empty or missing. We have not checked this output against a live onchain key.

Our app asks for 3 scopes, `CAST_ADD`, `REACTION_ADD` and `LINK_ADD`, for 7 days by default. The example in the official guide asks for 9 scopes and 30 days ([Docs issues #9](../docs-issues/)).

```ts title="client/src/signer.ts (condensed)"
const { currentUserNonce } = await api.signersByFid(fid);
const body = await makeKeyAddBody(
  { fid: BigInt(fid), key, scopes, ttl, nonce: currentUserNonce + 1, deadline: nowFc + 3600 },
  new ViemLocalEip712Signer(custodyAccount),      // custody key signs the two EIP-712 payloads
);
const msg = await makeKeyAdd(body.value, { fid, network: FarcasterNetwork.MAINNET }, appSigner); // app key signs the envelope
```

Call `makeKeyAddBody`. The older `getSignedKeyRequestMetadata` signs for the onchain contract, and the node rejects that inside a `KEY_ADD`.

:::danger[Your recovery phrase]
The two EIP-712 signatures need your custody key, which comes from your recovery phrase. Use a test account. Only type the phrase into code you have read, or code from people you trust. Do it on your own computer, as in [Your first cast](../first-cast/). Never paste it into an AI assistant. How our app handles it: [Before you start](../before-you-start/#seed-phrases-and-app-keys).
:::

## Step 2: Your node passes messages on

Send a signed message to `POST /v1/submitMessage` on your read node. The node validates it, then publishes it to the validators on the `mempool` gossip topic. The node does not hold on to it. Sources: [node-types: message submission](https://snapchain.farcaster.xyz/node-types#message-submission-and-the-mempool), and in the code, `submit_message_internal` in `src/network/server.rs` and `ReadNodeMempool` in `src/mempool/mempool.rs`.

An HTTP `200` therefore means the node found the message valid and sent it on. It does not mean a validator has put it in a block. To find out, ask for the message back. `/v1/info` on a read node shows `mempoolSize: 4294967295` for shards 1 and 2, a placeholder value.

This optional check sends 64 random bytes. It was the only write we sent to mainnet:

```bash title="Optional"
head -c 64 /dev/urandom | curl -s -X POST "$NODE/v1/submitMessage" \
  -H 'Content-Type: application/octet-stream' --data-binary @-
# HTTP 400: Invalid protobuf data: Unable to decode message
```

What our app does after you press Cast, Like, Recast or Follow (<RepoLink path="client/src/pending.ts" />):

1. Shows it right away, marked *sending*.
2. Sends the signed message. On `200` it shows *Accepted by the node for relay. Waiting to see it in a block.*
3. Every 4 seconds, asks the node for it by hash (`castById`, `reactionById`, `linkById`).
4. If the node still does not have it 30 seconds after the last send, sends the identical message again. It has the same hash, so it cannot appear twice.
5. After 4 sends it marks the message *failed* and says why. A `4xx` answer fails it at once, since an invalid message stays invalid.

We have not measured how long a valid message takes to appear.

## Step 3: Some parts live onchain

| Part | Where | What |
|---|---|---|
| Accounts | Contracts on OP Mainnet (IdRegistry, KeyRegistry, StorageRegistry) | Account numbers (FIDs), owner addresses, storage, keys added onchain |
| Messages | Snapchain | Casts, likes and recasts, follows, profile fields, verifications, gasless `KEY_ADD` |
| Apps | Anywhere | Apps like ours, reading from whichever node they choose |

Validators read the Farcaster contracts on OP Mainnet and put those events in blocks. Your node gets them inside the blocks, together with all messages. It needs no OP Mainnet connection of its own. Your account is not tied to an app. Any app that can reach a node can show your posts, and any app key you approved can post for you.

## Step 4: Account number, owner address, storage

- **FID** is your account number. It is registered onchain. Profiles, casts and follows all refer to it.
- **Custody address** is the Ethereum address that owns the FID. It approves and revokes app keys, and can move the FID to another address. Our app derives it from the recovery phrase at the path `m/44'/60'/0'/0/0`.
- **Storage** is paid for onchain, in units. Each unit holds a fixed number of each kind of message. Past that, the node deletes the oldest ([docs: Messages](https://docs.farcaster.xyz/learn/what-is-farcaster/messages)). Registering an FID and buying storage still cost gas. This guide does neither.

The per-unit numbers in the official docs are out of date ([Docs issues #20](../docs-issues/)). Your node has the current ones:

```bash
curl -s "$NODE/v1/storageLimitsByFid?fid=3" | jq
curl -s "$NODE/v1/userDataByFid?fid=3" | jq '.messages[].data.userDataBody'
```

## Step 5: Shards, validators and your node

| Question | Validator | Your read node |
|---|---|---|
| Makes blocks and votes on them | Yes | No |
| Has every message | Yes | Yes, downloaded from validators |
| Takes `submitMessage` | Yes, into its mempool | Yes, and sends it to validators |
| Rewards | Not covered here | None |
| Delay | Up to date | A little behind, by the time it takes to fetch each block ([node-types](https://snapchain.farcaster.xyz/node-types)) |

Messages are split across shards. Shard 0 holds network-wide data, including gasless `KEY_ADD` messages. Shards 1 and 2 split the accounts between them. `numShards` in `/v1/info` counts only the account shards, so it says 2 while `shardInfos` lists 3. Our node's database was 557.86 GB; on disk the shards took 37, 261 and 259 GiB.

```bash
curl -s "$NODE/v1/info" | jq '{version, numShards, shards: [.shardInfos[] | {shardId, maxHeight, blockDelay}]}'
```

`blockDelay` is how many seconds a shard's newest block is behind the clock. When every shard shows single digits, the node is synced ([Getting Started](https://snapchain.farcaster.xyz/getting-started)). A new node first downloads a snapshot. On 2026-10-18 that was 5689 compressed chunks, roughly 500 GB by our disk readings. Then it fetches the newer blocks one by one. Ours did 4.3 to 4.6 blocks a second per shard.

## Step 6: Read with the HTTP API

The node answers HTTP on port 3381. It has no "home feed" endpoint, so our app builds one (<RepoLink path="client/src/feed.ts" />):

```bash
# 1. Which FIDs does FID 3 follow?
curl -s "$NODE/v1/linksByFid?fid=3&link_type=follow&pageSize=5&reverse=true" \
  | jq '[.messages[].data.linkBody.targetFid]'

# 2. Newest casts from one FID
curl -s "$NODE/v1/castsByFid?fid=3&pageSize=3&reverse=true" \
  | jq '.messages[] | {fid: .data.fid, text: .data.castAddBody.text, hash}'

# 3. The next page: send nextPageToken back as pageToken
curl -s "$NODE/v1/castsByFid?fid=3&pageSize=3&reverse=true&pageToken=<nextPageToken>"
```

The app builds the feed in 3 parts:

1. Load the follow list.
2. For up to 40 of those FIDs, load the newest 10 casts, 6 requests at a time.
3. Sort by time.

 Times count seconds since 2021-01-01 00:00 UTC.

:::caution[Write `reverse=true`]
`reverse=1` gets HTTP 400 "provided string was not `true` or `false`", although one table in the docs uses it ([Docs issues #5](../docs-issues/)).
:::

## Step 7: Why the app and the node share one address

A page loaded over HTTPS cannot call `http://<ip>:3381`; browsers block that as mixed content. GET requests to another address work, because the node sends `Access-Control-Allow-Origin: *`. `submitMessage` does not. Its `Content-Type: application/octet-stream` header makes the browser send an `OPTIONS` request first. The node answers that with 404, so the browser blocks the post.

So Caddy serves the app and passes `/v1/*` to the node, on the same address (<RepoLink path="deploy/Caddyfile" />):

```text title="deploy/Caddyfile (excerpt)"
{$SITE_ADDRESS} {
	@admin path /v1/mesh /v1/mesh/*
	handle @admin {
		respond 404
	}

	handle /v1/* {
		reverse_proxy {$NODE_UPSTREAM:127.0.0.1:3381}
	}

	handle {
		root * {$CLIENT_ROOT:/srv/client}
		try_files {path} /index.html
		file_server
	}
	# plus security headers, including a CSP with connect-src 'self'
}
```

Through Caddy, `/v1/mesh` (the node's mesh debug view) returns 404. `/v1/currentPeers` stays public: it lists the peers the node is connected to, which are mainnet validators, with the addresses it sees for them. `connect-src 'self'` lets the page send requests only to its own address. If a library in the app were compromised, it could not send your data elsewhere. Caddy fetches its own Let's Encrypt certificate over ports 80 and 443.

## Step 8: Filters

Our app's filters work on casts made in any app, because they run on what your node returns (<RepoLink path="client/src/filters.ts" />).

| Rule | Effect |
|---|---|
| Mute FID, mute keyword | Hide casts that match |
| Only show FIDs, only show keywords | When set, hide every cast that does not match |

When a cast matches both, the mute wins. Keywords ignore case and match anywhere in the text. Filters are saved in your browser, and the feed shows how many casts it hid.
