We ran the 3 steps once, on mainnet, on 2026-10-18. Times are IST (UTC+5:30). The server was a Hetzner cax31 (ARM64, 8 vCPU, 16 GB RAM) in fsn1 with a 1000 GB volume and Ubuntu 24.04. The node ran Snapchain v0.14.3. The full notes are in <RepoLink path="MEASUREMENTS.md" /> and <RepoLink path="run-log.md" />. We replaced the server's IP, its Hetzner IDs and our test account with placeholders before publishing them.

## The run, start to finish

| Event | Date and time&nbsp;(IST) |
|---|---|
| Server rented with `provision.sh` | 2026-10-18 01:26 |
| Node fully synced, every shard less than 10 s behind | 2026-10-18 15:32 |
| Cast posted through the node | 2026-10-18 20:53 |
| Server and volume deleted with `teardown.sh` | 2026-10-20 23:30 |

The server ran for 70 h 04 m. From 15:32 on 2026-10-18 until shutdown, all 3 shards stayed at the tip. The last count, at 22:56 on 2026-10-20, was 914,276,853 messages in a 558 GB database. The run cost $11.49 ([Cost](#cost)). After `teardown.sh` the Hetzner project was empty. The screenshots on this page are from 2026-10-18.

## Posted to mainnet

| What | Time&nbsp;(IST) |
|---|---|
| Gasless `KEY_ADD` accepted: signer source `OFFCHAIN`, scopes `CAST_ADD`, `REACTION_ADD` and `LINK_ADD`, 1-day expiry, nonce 1 | 20:53:29 |
| Cast confirmed by the node | 20:53:47 |

The cast says "My first cast on a local node". Hash `0x4b4eb31bb28cf0d6d0583c7fc022a60f0af50ec2`. [See the cast](https://farcaster.xyz/nashrad/0x4b4eb31b).

The cast was confirmed 18 seconds after the key. The app ran on `localhost` on our own computer (client commit `7f2b71f`), with `SNAPCHAIN_NODE_URL` pointing at our node through Caddy. We typed the recovery phrase into that browser tab. It never left the browser: only the signed `KEY_ADD` and the cast went to the node. We have not sent a like, recast or follow on mainnet.

## The sync, from the log

A logger on our side read the disk and the node's `/v1/info` over SSH every 10 minutes. Some of its lines, with the memory and status fields cut:

```text title="run-log.md (excerpts)" wrap=false
03:13:11 IST progress: du=139G df=15% Progress: 1705/5689 chunks (29%) (ETA: 3h43m) info=none
08:37:12 IST progress: du=494G df=53% Progress: 5319/5689 chunks (93%) (ETA: 0h28m) info=none
12:41:33 IST progress: du=556G df=60% info=[{"s":0,"h":48251171,"d":45482},{"s":1,"h":48946704,"d":24543},{"s":2,"h":48763546,"d":43641}]
15:32    IST synced: /v1/info shard 0 h=48305951 blockDelay=1, shard 1 h=48980989 d=1, shard 2 h=48816538 d=4
16:20:25 IST progress: du=556G df=60% info=[{"s":0,"h":48308772,"d":4},{"s":1,"h":48983812,"d":1},{"s":2,"h":48819359,"d":0}]
```

`h` is a shard's block height and `d` its `blockDelay`, in seconds behind. At 12:41 the node was still about 12 hours behind on shard 0. At 15:32 every shard was within 4 seconds: that is the sync time in the table below. At 16:20 it was still at the tip.

| Phase | Time |
|---|---|
| `provision.sh` | 35 s (started 01:26:33) |
| Snapshot download | About 5 h 24 m for 5689 chunks, roughly 500 GB by our disk readings, about 25 MB/s |
| Snapshot load in total (download, gunzip, untar, shard by shard) | About 8 h 34 m |
| Catching up after the load | About 5 h 15 m, at 4.3 to 4.6 blocks a second per shard |
| From renting the server to fully synced (every shard less than 10 s behind) | 14 h 06 m |
| `deploy-client.sh`, including the Let's Encrypt certificate | About 35 s |

Problems we hit on the way, all on 2026-10-18, IST. Each has a fix on [Fix a problem](../fix/):

| Time | What happened |
|---|---|
| 01:20 | cx43 was not available to rent, so we rented cax31 |
| 01:23 | The 2000 GB volume went over the new-account limit; we used 1000 GB |
| 01:35 | SSH was refused: the machine running the steps kept getting new public IPs, so the firewall no longer matched |
| 01:44 | The disk was filling during the restore; we installed the two disk helpers by hand |
| 01:38 to 10:11 | The HTTP API did not answer while the snapshot loaded |
| 13:39 | `node.sh` stopped waiting at its old 12-hour limit; the node kept syncing |
| 18:48 | cax31 was not available to rent in fsn1, nbg1 or hel1 when we checked |
| Whole sync | The computer running the steps paused at least 13 times; the node kept going |

- No key or phrase in browser storage.

The live run used the earlier versions of `node.sh`, `watchdog.sh` and the firewall rules. Commands to rerun the suites:

### How to vouch

The checklist is in <RepoLink path="VOUCHER.md" />. In short:

1. Note the commit you used: `git rev-parse --short HEAD`.
2. Complete the [Full run](../quickstart/). Write down how long renting the server and the sync took, what Hetzner charged, the server type and the volume size.
3. Open the app from your node and check that a feed loads.
4. Optional, with a test account only: add an app key and send one cast ([Post with an app key](../first-cast/)). Note the cast hash and whether another app shows it.
5. Run `teardown.sh` and check in the Hetzner console that the project is empty.
6. Post what happened on Farcaster, including anything that broke.

Leave your recovery phrase, Hetzner token and server details out of the post.
