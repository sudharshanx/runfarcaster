**Set up with AI:** one prompt has Claude Code, Codex or Cursor run these 3 commands with you. [Get the prompt](../ai-assistant/).

Three commands rent a Linux server at Hetzner, start your own Snapchain read node on it, and open a web app on the same machine that shows your feed from that node. With an app key, the app also posts, likes and follows through your node ([Post with an app key](../first-cast/)).

Vouchers do this Full run. To test first, the [Instant run](../instant-run/) takes 5 minutes against a node that is already running. FID, read node, snapshot, `blockDelay`, `KEY_ADD`, custody address, Caddy and sslip.io are in the [Glossary](../glossary/).

:::note[Set up first]
- A Hetzner account with an empty project, and an API token for that project. [Server and node](../server-and-node/) shows how. In an empty project the scripts cannot touch a server, volume or firewall that someone else made.
- Room in your Hetzner volume quota for 1000 GB. New accounts may rent 1024 GB of volumes in total, across all projects, so a second node usually needs a higher limit ([Hetzner limits](../server-and-node/#hetzner-limits)).
- An SSH key uploaded to Hetzner. `hcloud ssh-key list` shows its name.
- A computer with bash, `hcloud`, `jq`, `ssh`, `curl` and Node.js 22.12 or later (22.x, 24.x or 26+). To install Node.js 24 with [nvm](https://github.com/nvm-sh/nvm#installing-and-updating), run `nvm install 24 && nvm use 24`, or download it from [nodejs.org](https://nodejs.org/en/download). Node.js 20.19 can run `npm run dev`, but not the tests that `deploy-client.sh` runs.

Get the code, set the token, then set the server options. The token prompt hides what you type. Replace `my-key` with your SSH key's name.

```bash title="your computer"
git clone {{REPO_URL}}
cd runfarcaster
read -rsp 'Hetzner token: ' HCLOUD_TOKEN && export HCLOUD_TOKEN && echo
MY_IP=$(curl -4 -s https://ifconfig.me) && echo "$MY_IP"
export NAME=snapchain-read-node SSH_KEY=my-key SERVER_TYPE="" VOLUME_GB=1000 WATCHDOG=0 SSH_SOURCE_CIDRS="$MY_IP/32"
```

`NAME` names the server; the volume and the firewall are named after it, and `teardown.sh` deletes by it. `SERVER_TYPE=""` lets the script pick the server type. `WATCHDOG=0` keeps the server until you delete it. `SSH_SOURCE_CIDRS` lets only your address reach SSH. These settings last for this terminal only; in a new terminal, run the last 3 lines again.
:::

## 1. Rent a server

If the project already has a server named `$NAME`, or the volume `$NAME-data`, `provision.sh` stops and changes nothing. That server may be someone else's. For a second node, pick another name (for example `export NAME=snapchain-read-node-2`) and keep it for teardown. To continue your own earlier run, use `REUSE=1 ./provision.sh`.

```bash title="your computer"
IP=$(./provision.sh) && echo "$IP"
```

**You will see** `[provision] server type …` with the type it picked, then `[provision] done. Next …` and the server's IP address. **Time:** under a minute.

Hetzner bills the server by the hour until you delete it. The tested type, cax31, was sold out on 18 Oct 2026, so expect cpx42 (x86, 16 GB RAM): about $0.255 an hour with the 1000 GB volume, or about $159 a month. **cpx42 has not been tested.** What step 1 does: [Server and node](../server-and-node/#what-step-1-does).

:::tip[Lost `$IP`?]
`$IP` only lives in the terminal where you set it. In a new terminal, run the `export NAME=…` line from **Set up first** again, then `IP=$(hcloud server ip "$NAME")`.
:::

<details>
<summary>How the server type is picked</summary>

With `SERVER_TYPE=""`, `provision.sh` tries cx43, cax31, cpx42 and ccx23 in that order and rents the first one for sale in `LOCATION` with at least 16 GB of RAM. It logs `skipping …` for each sold-out type. If none is for sale, it stops with `none of [...] is usable`, lists the types you can rent there, and creates nothing. Run step 1 again with one of them in `SERVER_TYPE`, or with another place in `LOCATION` (fsn1, nbg1, hel1, ash, hil or sin).

To see the pick and the price first, without creating anything: `ESTIMATE_ONLY=1 SERVER_TYPE="" VOLUME_GB=1000 ./provision.sh`.

</details>

<details id="try-it">
<summary>A trial server that deletes itself</summary>

Turn the watchdog on and set a price limit and the hours you expect to use:

```bash title="your computer"
IP=$(WATCHDOG=1 MAX_USD=5 EXPECTED_HOURS=16 ./provision.sh) && echo "$IP"
```

provision.sh then starts `watchdog.sh` in the background on your computer, before it creates anything. It deletes the server, the volume and the firewall at the first of these:
- 24 hours after it started, even if the node is healthy (`WATCHDOG_MAX_WALL_SECS` changes this, for example `172800` for 48 hours),
- when the bill would reach `MAX_USD`,
- when the node has made no progress for 2 hours.

A sync on cax31 takes about 14 hours, so the 24-hour default leaves about 10 hours with a synced node.

If the watchdog cannot start (for example `HCLOUD_TOKEN` is missing), step 1 stops with an error and creates nothing. Its output is in `.provision-state/watchdog.out` and its log in `.provision-state/watchdog.log`.

The progress check reads the database size and block heights over SSH with `SSH_KEY_FILE`, the private half of the key you uploaded to Hetzner. It defaults to `~/.ssh/id_ed25519` if that file exists. Without a key file only the price and time limits apply. If SSH stops working (for example your home IP changed), the watchdog logs a warning and keeps the server.

To keep the node after all, stop the watchdog without deleting anything: `touch .provision-state/watchdog.disarm`.

</details>

<details>
<summary>A 2 TB volume instead</summary>

Run step 1 as `IP=$(VOLUME_GB=2000 ./provision.sh)`. It needs a Hetzner volume limit above 2000 GB and has not been tested. The price list puts it at about $0.29 an hour.

</details>

## 2. Start the node

This uses `$IP` from step 1, in the same terminal.

```bash title="your computer"
ssh root@$IP \
  "SNAPCHAIN_AGREE_NO_REWARDS=yes MIN_FREE_GB=900 bash -s" \
  < node.sh
```

**You will see** `[node.sh] Node is in sync.`, then a health check with `sync: SYNCED`. **Time:** on a server with 8 cores and 16 GB of RAM (Hetzner cax31), expect loading the snapshot to take about 8 to 9 hours and catching up about 5 more. A faster disk or network shortens both. Times on cpx42 and other types have not been measured. What step 2 does: [Server and node](../server-and-node/#what-step-2-does).

Right after step 1, SSH can refuse the connection for a minute while the server boots. Wait and run it again. On the first connection SSH asks you to confirm the server's fingerprint; type `yes`.

<details>
<summary>If SSH drops, or to check progress</summary>

The node keeps going on the server. Reconnect and wait for it again:

```bash
IP=$(hcloud server ip "$NAME")   # only in a new terminal, after export NAME=…
ssh root@$IP 'bash -s wait' < node.sh
```

To check progress:

```bash
ssh root@$IP 'curl -s 127.0.0.1:3381/v1/info' | jq '.shardInfos[] | {shardId, blockDelay}'
```

Synced means every shard shows a `blockDelay` in single digits ([Getting Started](https://snapchain.farcaster.xyz/getting-started)). The API does not answer while the snapshot loads.

</details>

## 3. Open the app

```bash title="your computer"
./deploy-client.sh "$IP"
```

**You will see** `[deploy-client] OK: https://<name> (client) …`. Open that address: the status at the top says **Connected to your node**. **Time:** under a minute with a warm npm cache. The first build takes longer.

Step 3 can run before step 2 finishes, in a second terminal, while the node is still loading its snapshot (set `NAME` and `IP` there as in **Lost `$IP`?**). The script then ends with `[deploy-client] OK: app is up at https://<name>. The node isn't answering yet`, and the app shows **Node still starting** until the node's API answers.

To post, add an app key: [Post with an app key](../first-cast/). What step 3 does: [Server and node](../server-and-node/#what-step-3-does).

To build your own app, bot or analytics job on the node, start with [Build on your node](../build-on-your-node/).

<details>
<summary>Use your own domain</summary>

Point the domain at `$IP` and pass it as a second argument: `./deploy-client.sh "$IP" node.example.com`. Without one, the script uses `<ip-with-dashes>.sslip.io`, a free DNS service run by someone else. That is fine for reading. To add a key with your recovery phrase, use the local copy from [Post with an app key](../first-cast/).

</details>

<CopyPrompt id="client" />

:::caution[When you are done: delete everything]
```bash title="your computer"
CONFIRM="$NAME" ./teardown.sh
```

This deletes the server, the volume and the firewall, with the node's database. It keeps the SSH key you uploaded, and running it twice is safe. If `provision.sh` in this folder recorded a different ID for the server named `$NAME`, that server is not the one you created, so `teardown.sh` stops and deletes nothing. `OTHER_SERVER_OK=1` overrides this. Read the script first: <RepoLink path="teardown.sh" />. `teardown.sh` has been tested only with `DRY_RUN=1` and a fake `hcloud`, not against real servers yet, so check the [Hetzner console](https://console.hetzner.cloud/) afterwards.
:::
