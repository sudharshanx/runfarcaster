You rent a Linux server at Hetzner and run a Snapchain read node on it. A small web app sits in front of the node. The node first loads a snapshot of the network, which took us 8 h 34 m, then catches up block by block. The app runs in your browser and reads from your node alone.

You need:

- A Hetzner API token in `HCLOUD_TOKEN`.
- An SSH key uploaded to Hetzner.
- `hcloud`, `jq`, `ssh` and `curl`.
- Node.js 22.12 or later (22.x, 24.x or 26+) with npm.

[Do it on Hetzner](../hetzner/) walks through each one. [Before you start](../before-you-start/) explains costs and safety, and the [Glossary](../glossary/) explains the terms. To let a coding assistant drive, see [Do it with your AI assistant](../ai-assistant/).

## 1. Rent a server

Find your public IP so only you can reach SSH, then rent the server:

```bash title="your computer"
MY_IP=$(curl -4 -s https://ifconfig.me)
echo "$MY_IP"
```

Replace `my-key` with the name `hcloud ssh-key list` shows.

Server types sell out. On 18 Oct 2026 at 18:48 IST, Hetzner listed cax31 as sold out in fsn1, nbg1 and hel1, the only places that offer it. If step 1 stops with `not available in fsn1 right now`, the error lists the types with at least 16 GB of RAM that you can rent there, cheapest first. Run step 1 again with one of them in `SERVER_TYPE`, or with another place in `LOCATION` (fsn1, nbg1, hel1, ash, hil or sin). We have only run the node on cax31.

With `WATCHDOG=0` the server keeps running until you delete it. If you only want to try it, provision.sh can delete the server for you after a set time; see [If you only want to try it](#if-you-only-want-to-try-it). Read the script first: <RepoLink path="provision.sh" />

What it does:
- Checks that each entry in `SSH_SOURCE_CIDRS` looks like an address with a prefix, such as `203.0.113.7/32`. An empty `$MY_IP` stops it here.
- Checks that `LOCATION` exists and that the server type is for sale there with at least 16 GB of RAM. If not, it lists what is available and creates nothing.
- Reads the hourly price from Hetzner's live price list and prints it. It stops before creating anything if that price × `EXPECTED_HOURS` (default 6) is above `MAX_USD` (default 2, in your account's currency).
- Creates a firewall, the data volume and the server. The firewall opens SSH (22, only to `SSH_SOURCE_CIDRS`), gossip (3382/udp) and the web ports 80 and 443. The node's own API ports 3381 and 3383 stay closed; the app reaches the node through Caddy.
- Starts `watchdog.sh` first, unless you set `WATCHDOG=0` (see [If you only want to try it](#if-you-only-want-to-try-it)).
- Prints the server's IP. Running it again reuses what exists and does not start a second watchdog.

What it prints (shortened; the lines come from the script's log calls):

```text
[provision] server type cax31: 8 vCPU (shared), 16 GB RAM, 160 GB disk, arm
[provision] local disk 160 GB < 2000 GB: adding a 1000 GB volume
  total       ~0.164 /h
[provision] cost guard OK: projected <= MAX_USD=2
[provision] WATCHDOG=0: no watchdog started (no automatic spending cap).
[provision] done. Next (in a new terminal, get the IP back with: IP=$(hcloud server ip snapchain-read-node)):
```

It took 35 s for us.

Check it worked:

```bash
hcloud server list      # snapchain-read-node, running
hcloud volume list      # snapchain-read-node-data, 1000 GB
```

Hetzner bills the server by the hour from now on. For cax31 with the 1000 GB volume that is about $0.164 an hour, or about $102 a month if you keep it.

:::tip[Lost `$IP`?]
`$IP` only lives in the terminal where you set it. In a new terminal, or after a reconnect, run `IP=$(hcloud server ip snapchain-read-node)`.
:::

## 2. Start the node

```bash title="your computer"
IP=$(hcloud server ip snapchain-read-node)
ssh root@$IP \
  "SNAPCHAIN_AGREE_NO_REWARDS=yes MIN_FREE_GB=900 bash -s" \
  < node.sh
```

Right after step 1, SSH can refuse the connection for a minute while the server boots. Wait and run it again. On the first connection SSH asks you to confirm the server's fingerprint; type `yes`.

Read the script first: <RepoLink path="node.sh" />. It downloads and runs the official [`snapchain-bootstrap.sh`](https://github.com/farcasterxyz/snapchain/blob/main/scripts/snapchain-bootstrap.sh) and prints that file's sha256.

What it does:
- Checks Ubuntu 22.04 or 24.04, RAM and free disk. `MIN_FREE_GB=900` lets it accept the 1000 GB volume, which shows 984 GB.
- Installs Docker from Docker's own apt repository.
- Writes the two answers the bootstrap would ask for into `~/snapchain/.env`: that you get no rewards, and `SKIP_CRONTAB=true` unless you set `OPERATOR_FID`.
- On a disk under 1500 GB, installs two helpers. `disk-guard.sh` stops the node at 90% full. `snapshot-space-saver.sh` deletes snapshot files the node has already read.
- The helpers are needed because the official restore keeps all chunks, one tar per shard and the database until it finishes. That does not fit on 1 TB.
- Runs the official bootstrap. It needs a terminal, so `node.sh` gives it one with `script`, and stops following its log once it prints "Upgrade complete".
- Checks `/v1/info` once a minute. It stops when every shard is under 10 s behind on 3 checks in a row, or after 24 hours. Then it prints a health check.

:::caution[New, not yet run live]
In our live run we installed the two disk helpers by hand. `node.sh` now installs them itself; that code has unit tests (`test/node_sh_test.sh`) but has not run during a real sync yet.
:::

What it prints while syncing (the format is from `node.sh`; shard numbers are from our run at 10:34 IST, clock times are examples):

```text
[node.sh] Data disk 984 GB: arming disk-guard and snapshot-space-saver.
[node.sh] disk-guard: snapchain-disk-guard.timer is active.
[node.sh] space-saver: snapchain-space-saver.service is active.
[node.sh] Waiting for sync: all shards blockDelay < 10s for 3 polls (timeout 86400s).
[node.sh] 04:31:10Z HTTP API not answering yet (snapshot download in progress?).
[node.sh] 05:04:36Z SYNCING shard 0: height=48210601 blockDelay=79236 | shard 1: height=48906556 blockDelay=57766 | shard 2: height=48723458 blockDelay=76739
...
[node.sh] Node is in sync.
================ Snapchain health check ================
HTTP API http://127.0.0.1:3381/v1/info: OK
sync: SYNCED (blockDelay < 10s on all shards)
```

Ours took 14 h 06 m from renting the server. Loading the snapshot took 8 h 34 m. Catching up took 5 h 15 m. The API does not answer while the snapshot loads; that is normal.

If your SSH session drops, the node keeps going on the server. Reconnect and wait for it again:

```bash
IP=$(hcloud server ip snapchain-read-node)
ssh root@$IP 'bash -s wait' < node.sh
```

Check it worked:

```bash
ssh root@$IP 'curl -s 127.0.0.1:3381/v1/info' | jq '.shardInfos[] | {shardId, blockDelay}'
```

Synced means every shard shows a `blockDelay` in single digits ([Getting Started](https://snapchain.farcaster.xyz/getting-started)).

## 3. Open the app

```bash title="your computer"
IP=$(hcloud server ip snapchain-read-node)
./deploy-client.sh "$IP"
```

If you own a domain, point it at `$IP` and pass it as a second argument: `./deploy-client.sh "$IP" node.example.com`.

Read the script first: <RepoLink path="deploy-client.sh" />, <RepoLink path="deploy/Caddyfile" />

What it does:
- Builds the app on your computer (`npm ci --ignore-scripts`, tests, `vite build`). Needs Node.js 22.12 or later (22.x, 24.x or 26+).
- Copies the built app, the Caddyfile and a compose file to `/opt/snapchain-client` on the server and starts Caddy.
- Caddy gets a Let's Encrypt certificate and serves the app plus `/v1/*` (passed to the node on `127.0.0.1:3381`) from one HTTPS address.

Without your own domain it uses `<ip-with-dashes>.sslip.io`, a free DNS service run by someone else. That is fine for reading. For adding a key with your recovery phrase, use the local copy described in [Your first cast](../first-cast/).

What it prints:

```text
[deploy-client] building client (npm ci --ignore-scripts, typecheck, tests, build)
[deploy-client] uploading to root@<ip>:/opt/snapchain-client
[deploy-client] waiting for HTTPS on https://<ip-with-dashes>.sslip.io ...
[deploy-client] OK: https://<ip-with-dashes>.sslip.io (client) and https://<ip-with-dashes>.sslip.io/v1/info (node, proxied)
```

It took 35 s for us with a warm npm cache. The first `npm ci` takes longer.

Check it worked (use the address it printed):

```bash
curl -sI https://<name>/ | grep -i content-security-policy   # connect-src 'self'
curl -s https://<name>/v1/info | jq .version                 # your node, through Caddy
```

Open the address in a browser. The status line should start with `Connected. version 0.14.3;` and list how far behind each shard is. Type an FID (try `3`) under Feed and press Refresh.

## How the pieces fit

- The read node has no account with anyone. It gets blocks from the validators over gossip on UDP 3382.
- The app is static files. Every request goes to `/v1/*` on the same address it came from, so the browser never makes a cross-site call.
- To post you need an app key. See [Your first cast](../first-cast/) and the [Tutorial](../tutorial/#step-1-app-keys-are-gasless-now).

## If you only want to try it

provision.sh can delete the server for you after a set time. Leave out `WATCHDOG=0` in step 1 and set a price limit and the hours you expect to use. This is the command we ran:

```bash title="your computer"
IP=$(SSH_KEY=my-key \
  SERVER_TYPE=cax31 \
  VOLUME_GB=1000 \
  MAX_USD=5 \
  EXPECTED_HOURS=16 \
  SSH_SOURCE_CIDRS="$MY_IP/32" \
  ./provision.sh)
```

provision.sh then starts `watchdog.sh` in the background on your computer, before it creates anything. The watchdog deletes the server, the volume and the firewall at the first of these:
- 24 hours after it started, even if the node is healthy (`WATCHDOG_MAX_WALL_SECS` changes this, for example `172800` for 48 hours),
- when the bill would reach `MAX_USD`,
- when the node has made no progress for 2 hours.

Our sync took 14 hours, so the 24-hour default left us about 10 hours with a synced node.

If the watchdog cannot start (for example `HCLOUD_TOKEN` is missing), step 1 stops with an error and creates nothing. Its output is in `.provision-state/watchdog.out` and its log in `.provision-state/watchdog.log`.

The progress check reads the database size and block heights over SSH with `SSH_KEY_FILE`, the private half of the key you uploaded to Hetzner. It defaults to `~/.ssh/id_ed25519` if that file exists. Without a key file only the price and time limits apply. If SSH stops working (for example your home IP changed), the watchdog logs a warning and keeps the server.

To keep the node after all, stop the watchdog without deleting anything: `touch .provision-state/watchdog.disarm`.

## Delete everything

When you no longer need the node, delete it. Read the script first: <RepoLink path="teardown.sh" />

```bash title="your computer"
CONFIRM=snapchain-read-node ./teardown.sh
hcloud server list && hcloud volume list     # snapchain-read-node should be gone
```

This deletes the server, the volume and the firewall. The node database is on the volume, so it goes too. The script then lists what is left, and fails if any of the three remain. Running it twice is safe: the second run reports each item as not found. It keeps the SSH key you uploaded. Check the [Hetzner console](https://console.hetzner.cloud/) for anything else left in the project.

:::caution
We have run `teardown.sh` only in `DRY_RUN=1` mode and against a fake `hcloud` in tests, not against real servers yet.
:::
